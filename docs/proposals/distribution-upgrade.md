# Distribution upgrade — brew + apt + cask for the portfolio

**Status:** draft / mulling. Not committed work.

Sketches the next-step upgrades to how this repo's release pipelines
get binaries into users' hands. Captures current state, ideas
discussed, and a phasing proposal. No implementation work tracked
yet — when this matures into a plan, promote to `done/` and open
the corresponding stack-row issues.

## Current state (what ships today)

### Rust CLIs (rust-cli stack)

Per-release artifact:

```
<bin>-<rust-target>.tar.gz   # 4 typical targets:
                             #   aarch64-apple-darwin
                             #   x86_64-unknown-linux-gnu
                             #   aarch64-unknown-linux-gnu
                             #   (+ optionally x86_64-apple-darwin if a project adds it)
```

Tarball contents: **just the binary**, in a `<bin>/<bin>` subdir
(canonical) or flat-at-root (legacy). Nothing else.

10 formulas in the shared tap `arthur-debert/homebrew-tools`:
`dodot`, `padz`, `rustloc`, `simple-gal`, `lexd`, `treex`,
`dotcat`, `nanodoc`, `too`, `burgertocow`. All generated by
`render-brew-formula` composite and pushed by `push-brew-tap`.
Install line:

```ruby
def install
  executable = Dir["*/padz"].find { |path| File.file?(path) } ||
               (File.exist?("padz") ? "padz" : nil)
  bin.install executable
end
```

i.e. **binary only**. No man pages, no shell completions, no
`.deb`, no `.rpm`, no AUR, no apt repo.

### GUI apps (electron-app + tauri-app stacks)

- `lex-fmt/lexed` (electron-app `@v1`): ships signed + notarized
  per-arch `.dmg` on every release. Asset is on the GH release
  page; users download manually and drag to `/Applications`.
- `arthur-debert/phos-app` (tauri-app `@v1` slice 1): will ship
  signed + notarized per-arch `.dmg` once first release cuts.
- `arthur-debert/simple-gal-ui` (electron-app, pending
  migration): not yet signed.

No casks in `homebrew-tools`. No `brew install --cask`
equivalent today; users go through the GH release page.

## Goals

User-facing CLIs that benefit from full packaging:

- `lexd` (lex-fmt/lex)
- `lex-lsp` (lex-fmt/lex — language server; mostly editor-internal
  but ad-hoc `brew install` would be useful)
- `padz` (arthur-debert/padz)
- `rustloc` (arthur-debert/rustloc)
- `simple-gal` (arthur-debert/simple-gal)
- `dodot` (arthur-debert/dodot)

Plus the other 4 current tap occupants (`treex`, `dotcat`,
`nanodoc`, `too`, `burgertocow`) — same upgrade applies.

GUI apps that benefit from `brew install --cask`:

- `lexed`
- `phos-app`
- `simple-gal-ui` (once migrated)

Target per-CLI deliverables:

1. **Binary** (already shipped)
2. **Man page** (`<bin>.1` — currently missing)
3. **Shell completions** — bash, zsh, fish (currently missing)
4. **`.deb` package** with all of the above, per-arch (currently
   missing)

Target per-GUI deliverables:

1. **Signed + notarized `.dmg`** (already shipped for lexed; coming
   for phos; pending for simple-gal-ui)
2. **Brew cask** that pulls the `.dmg` from GH release and
   installs the `.app` into `/Applications` (currently missing)

## Research: tooling landscape

### `cargo-deb` v3.7.0

- Mature, focused. Generates `.deb` from `Cargo.toml`
  `[package.metadata.deb]`.
- Supports assets (binary + man + completions + systemd units),
  debug-symbol split, conf-files.
- Doesn't do anything else. Pure `.deb`.

### `dist` (formerly `cargo-dist`) v0.31.0 by axodotdev

- Cross-compiles for multiple targets.
- Generates shell installer (`curl … | sh`), PowerShell installer,
  MSI on Windows, npm wrapper, **Homebrew formula** (full
  generation + push to a tap).
- Does **NOT** do `.deb`, `.rpm`, AUR, apt, Docker, Flatpak,
  cask, DMG, PyPI, winget — all listed as "Future Installers".
- Renamed from `cargo-dist` to `dist` (project rename in 2025,
  GitHub repo URL unchanged).
- Astral (the Ruff company) maintains a fork from which features
  get merged back upstream.

### Buy-vs-build for this portfolio

| Concern                                           | dist                                  | cargo-deb  | Our `rust-cli.yml`                               |
| ------------------------------------------------- | ------------------------------------- | ---------- | ------------------------------------------------ |
| Cross-compile + tarball                           | ✅                                    | —          | ✅ (today)                                       |
| Homebrew formula + push                           | ✅                                    | —          | ✅ (our `render-brew-formula` + `push-brew-tap`) |
| Shell / PS installer                              | ✅                                    | —          | ❌ (we don't have this)                          |
| **`.deb`**                                        | ❌                                    | ✅         | ❌                                               |
| Cascade-handler / `workflow_dispatch` integration | ❌ (opinionated about workflow shape) | irrelevant | ✅ portfolio-specific                            |
| Layer 0 release primitives integration            | ❌                                    | irrelevant | ✅ (Mode B in stack workflows)                   |

**Decision (tentative):** use `cargo-deb` for `.deb`; do NOT
migrate to `dist`. Reasoning:

1. `dist` would replace ~70% of `rust-cli.yml`'s current code but
   the remaining 30% (cascade-handler integration, Layer 0 mode,
   our shared tap pattern, npm/wasm publish slot) is the
   load-bearing portfolio-specific glue.
2. Migrating 6 rust-cli consumers (Cargo.toml metadata blocks,
   rewritten thin callers, version pin to a particular `dist`
   release) is non-trivial coordination cost.
3. Even if we adopted `dist`, we'd still need `cargo-deb` on top
   for `.deb`. We don't escape one of the tools.

Reconsider `dist` when: we hit 8+ rust-cli consumers AND need
a `dist`-only feature (shell installer, PS installer, MSI) we
don't have. Then the migration math shifts.

## Phasing proposal

### Phase 0 — Brew cask path (GUI apps)

Orthogonal to the CLI work. Smallest surface area, immediate
win for `lexed` (already produces signed+notarized `.dmg`s).

- New composite action: `render-brew-cask` (parallel of
  `render-brew-formula`). Inputs: `cask-name`,
  `app-bundle-name`, `bundle-id`, per-arch URLs + SHAs.
- Generalize `push-brew-tap` to accept `target-dir` input
  (`Formula/` vs `Casks/`).
- Update `electron-app.yml` + `tauri-app.yml` with optional
  inputs: `cask-name`, `cask-app-bundle`, `cask-bundle-id`,
  `tap-repo`. When set, post-build step computes per-arch
  `.dmg` SHA, renders cask, pushes to tap.

After: `brew install --cask arthur-debert/homebrew-tools/lexed`
just works.

### Phase 1 — `.deb` via cargo-deb

- `rust-cli.yml` linux build jobs install + run cargo-deb.
- Per-project Cargo.toml gets a `[package.metadata.deb]` block
  (boilerplate, ~15 lines).
- Output: `<bin>_<version>_<arch>.deb` attached to GH release.
- Users `apt install ./<bin>.deb`.

### Phase 2 — Man pages + shell completions in tarballs

Tarball layout extension (backward compatible):

```
<bin>-<target>/
├── <bin>
└── share/
    ├── man/man1/<bin>.1
    └── <bin>/completions/
        ├── <bin>.bash
        ├── _<bin>          # zsh
        └── <bin>.fish
```

Two paths for generating these:

- **(a) `clap_mangen` + `clap_complete` in `build.rs`** — clean
  Rust-side, ~30 LoC per project. Requires the CLI's clap
  `Command` to be reachable from `build.rs` (function in
  `cli.rs` etc.).
- **(b) Post-build via `<bin> generate-completions <shell>` /
  `<bin> man`** — workflow-side, no Rust changes, requires
  the CLI to support such a subcommand.

Update `rust-cli.yml`'s tarball-assembly step to include
`share/` if present.

Update `render-brew-formula` template to add:

```ruby
share_root = Dir["*/share"].first
if share_root
  man1.install Dir["#{share_root}/man/man1/*.1"]
  bash_completion.install Dir["#{share_root}/<bin>/completions/<bin>.bash"]
  zsh_completion.install Dir["#{share_root}/<bin>/completions/_<bin>"]
  fish_completion.install Dir["#{share_root}/<bin>/completions/<bin>.fish"]
end
```

`cargo-deb`'s `[package.metadata.deb].assets` picks up the same
files for the `.deb` via standard Debian paths.

### Phase 3 — `brew-tap.yml` validation workflow

Reusable workflow that runs ON the tap repo
(`arthur-debert/homebrew-tools`). Scope:

- `brew audit --strict --new-formula Formula/<changed>.rb` on
  PRs touching `Formula/` or `Casks/`
- Smoke install in clean Docker per formula:
  `brew install <tap>/<formula>` + sanity check (`<bin>
--version`, `man <bin>` not 404, completion file exists)
- Optional periodic stale-formula sweep (cron): detect upstream
  tag deletions

### Phase 4 (parked / "if we want it later")

- Shell installer (`curl … | sh`) for the rust-cli stack
- Hosted apt repo (signed via GPG, served via gh-pages or a
  static host) — `apt-add-repository deb https://… stable main`
- AUR (Arch User Repository) packages
- Windows: Chocolatey, winget, or just signed MSI

These each have their own packaging story; defer until a
specific use case asks.

## Open questions / decisions deferred

1. **Phase 2 path (a) or (b)?** `build.rs` + clap generators
   vs runtime `generate-completions` subcommand. (a) is more
   portable (any clap CLI), (b) is less work (no Rust changes)
   but requires the binary to grow a subcommand.

2. **Per-project Cargo.toml `[package.metadata.deb]` block**:
   templated/swept by `bin/sweep-github-policy` (treat as policy
   file), or hand-maintained per consumer? Sweep is consistent
   but adds T-flag-style drift surface.

3. **Cask `bundle-id` and `app-bundle-name`**: where do they live?
   Inputs in the caller workflow.yml, or auto-detected from
   `package.json` (electron) / `tauri.conf.json` (tauri)?

4. **Tap layout for casks**: `Casks/` (matches homebrew-cask
   convention) confirmed; do we segregate beta casks the way
   `homebrew-tools` already has a `beta/` directory for
   formulas?

5. **Notarization gate for casks**: refuse to push the cask if
   notarization didn't happen? Probably yes — an un-notarized
   cask installs an .app Gatekeeper will refuse to launch.
   Useful failure mode is at release time, not install time.
